= Hacking on nREPL
:description: Building, testing, documenting and releasing nREPL itself.

This section is dedicated to people who're hacking on nREPL itself (e.g. to fix bugs or to enhance
existing functionality).

There are generally two approaches to hacking on nREPL - you can either make some changes, build a new server
and run it locally to test your changes (e.g. via `clj`) or you can hack on nREPL in the classic
interactive Lisp manner and just make some changes and test them directly from a running (n)REPL.

== Building nREPL

Building nREPL locally is a very simple process:

. Clone the repo
. Make sure you have Clojure CLI installed
. Run the build:

[source,shell]
----
$ make install
----

That installs nREPL as version `99.99` into your local Maven repository
(set `PROJECT_VERSION` to pick another one), so afterwards you can simply
do something like:

[source,shell]
----
$ clj -Sdeps '{:deps {nrepl/nrepl {:mvn/version "99.99"}}}' -M -m nrepl.cmdline --interactive
----

Now you can start playing with the server you've built.

=== Building libnrepl native agent

NOTE: The reason why nREPL needs a native agent is explained
xref:installation.adoc#jvmti[here].

Native binaries of https://github.com/nrepl/nrepl/tree/master/libnrepl[libnrepl
JVMTI agent] are built on
https://github.com/nrepl/nrepl/actions/workflows/libnrepl.yml[CI] and then
copied into the https://github.com/nrepl/nrepl/tree/master/res[res/] directory
manually, so to do regular nREPL builds you don't have to recompile native code.
However, if you want to experiment with the agent yourself, then you can rebuild
the native library for your current platform like this:

[source,shell]
----
$ cd libnrepl/
$ make all
----

The Makefile will use the default C compiler for your OS (GCC on Linux, Clang on
MacOS). You will also need `JAVA_HOME` environment variable to be pointing at
the JDK installation. After the binary is built, copy it from `libnrepl/build/`
directory into `res/` and restart the REPL. The new binary will be picked up
automatically.

== Interactive Hacking

As nREPL is fundamental to the development workflows of many people it might be
unclear how exactly you can hack on it, while at the same time you're already
running an nREPL server, powering the REPL in which you're doing the hacking.

Developing nREPL while connected to nREPL is a classic example of eating your own dog food.

The development process is actually pretty simple - you just need to
connect to nREPL as you'd normally would (e.g. by using CIDER, vim-iced or Calva), make
some changes and test them by starting new nREPL instances from the
REPL and connecting to them to see how they are behaving.

In practice it might not be convenient to spin many nREPL connections
from your editor, so a combination of `nrepl.server/start-server` and
`nrepl.core/connect` is a very good alternative.

[source,clojure]
----
;; first we have to start a new server
=> (require '[nrepl.server :refer [start-server stop-server]])
nil
=> (def server (start-server :port 7888))
='user/server
=> (require '[nrepl.core :as nrepl])
nil
;; now you can connect to the server and send it some messages
=> (with-open [conn (nrepl/connect :port 7888)]
     (-> (nrepl/client conn 1000)    ; message receive timeout required
         (nrepl/message {:op "eval" :code "(+ 2 3)"})
         nrepl/response-values))
;; when you're done with a server you can stop it
=> (stop-server server)
----


NOTE: You don't really need an nREPL-powered REPL for this
workflow. It's going to work in exactly the same manner regardless of
the REPL you're using.

== Running the tests

The primary way to run tests is using Kaocha. The following command runs
the test suite on latest configured Clojure version:

[source,shell]
----
$ make test
----

The following command is useful while actively working on the codebase:

[source,shell]
----
$ clojure -M:dev:test --watch --skip-meta :slow
----

as it will re-run tests on changes, but also skip a handful of slower tests.

=== Running tests on CI

For ease of use/consistency with other nREPL projects, tests are run on CI
environments using Make, with the command:

[source,shell]
----
$ make test
----

All of CI is one GitHub Actions workflow, `.github/workflows/ci.yml`, and a pull
request runs only the pipelines its changed files touch. A `changes` job sorts
the diff into JVM files (`src/java`, `.clj`, `deps.edn`, `build`, `Makefile`,
the clj-kondo and cljfmt configs), CLR files (`src/csharp`, `.cljr`,
`deps-clr.edn`), shared files (`.cljc`, `test/clojure/nrepl/test_helpers`,
`ci.yml` itself) and docs (`doc`, `.md`, `.adoc`, `plan`). JVM or shared changes
run the JVM matrix on Linux and Windows; CLR or shared changes run .NET 8 on
Linux and Windows; the lint job runs whichever of `make lint`,
`make verify-cljdoc`, `make kondo-clr` and `make verify-docs` the changes call
for; codespell and misspell always run. The macOS legs and the informational
.NET 10 legs run only in a full run: every push to `master`, a manual dispatch,
or a pull request carrying the `ci:full` label (GitHub reads the label when the
pull request is opened, reopened or pushed to, so add it before that event). A
new push to a branch cancels the run still going for it.

=== Running the CI matrix locally

`make ci-local` runs every Linux leg of `.github/workflows/ci.yml` in parallel
in Podman containers, from your working checkout, and prints a table of tests,
assertions, failures and errors per leg. The legs, JDKs, Clojure versions and
commands come from the workflow files, so the two cannot drift. Windows and
macOS legs stay on GitHub Actions.

[source,shell]
----
$ make ci-local                                   # every leg
$ make ci-local LEG=1.12-temurin-8                # one leg
$ make ci-local LEG=lint                          # lint, kondo-clr, verify-cljdoc, verify-docs
$ make ci-local LEG=clr-net8                      # also clr-net10 (informational, as on CI)
$ make ci-local LOOP=200 TEST=nrepl.socket-test   # one namespace, 200 times in one JVM
----

Each leg writes its output to `target/ci-local/<leg>.log`. `LOOP` runs on
`1.12-temurin-21` unless you pass `LEG=` (JVM legs only) and exits nonzero if
any run failed, printing the first failing run. `JOBS=N` sets how many legs
run at once (default 8), `LEG_CPUS=N` (default 2, 0 for no limit) caps the CPUs of each leg. See `plan/verify/README.org` for the requirements and how the
containers are laid out.

== Running cljfmt

Our CI build enforces consistent indentation in all source files using `cljfmt`. You can run it
locally using:

[source,shell]
----
$ make cljfmt
----

You can have cljfmt fix indentation problems like this:

[source,shell]
----
$ clojure -M:cljfmt fix
----

== Running Eastwood

Our CI build enforces some lint checks via `Eastwood`. You can run it
locally using:

[source,shell]
----
$ make eastwood
----

== Regenerating the Built-in Ops Documentation

If you've made any changes to the built-in middleware descriptors you can regenerate their documentation using:

[source,shell]
----
$ make docs
----

== Releasing nREPL

NOTE: This section is relevant only to nREPL maintainers with push access to the repository.

Here's the process for cutting a new release (e.g. version `1.6.0`):

. Update `CHANGELOG.md`: rename the `master (unreleased)` section to
the new version and date (e.g. `1.6.0 (2026-02-26)`), and add a fresh
`master (unreleased)` section above it.

. In `doc/antora.yml`, set `version` to the major.minor version, quoted
(e.g. `"1.6"` for a `1.6.0` or `1.6.1` release; unquoted, YAML reads `2.0` as
the number 2). Do not include the patch number. Set `nrepl-version` under
`asciidoc.attributes` to the full version, so the manual's snippets pin the
release. A tag can't be fixed after the fact, and nothing in this repository
checks that the version was set before you tag.

. Bump the two versions the attribute can't reach: the example in the
`nrepl.tls-client-proxy` namespace docstring and the sample `describe`
response in `building_clients.adoc`.

. Commit and tag:
+
[source,shell]
----
$ git commit -am "Release 1.6.0"
$ git tag v1.6.0
----

. Reset `version` in `doc/antora.yml` back to `~` and commit:
+
[source,shell]
----
$ git commit -am "Begin next development iteration"
----

. Push the commits and tag:
+
[source,shell]
----
$ git push origin master --tags
----

. Nothing else happens automatically. This repository has no release
automation: pushing the tag does not deploy to Clojars and does not create a
GitHub Release.

. Add the new tag to the `tags` list in the
https://github.com/nrepl/nrepl.org/blob/master/antora-playbook.yml[nrepl.org
playbook]. The site only builds the tags listed there, so the release's docs
won't show up in its version menu until you do.
